* **Status:** Accepted
* **Date:** 2026-11-04
* **Deciders:** Team / Project Lead

## 1. Context and Problem Statement

Feature **S-3** and **C-5** in `docs/spec.md` require importing past message history for picked chats:
1. **History Import UI & Controls ([Section 7 S-3](file:///Users/van.tran/Documents/dev/chat-bridge/docs/spec.md#L173), [Section 10](file:///Users/van.tran/Documents/dev/chat-bridge/docs/spec.md#L280)):** The sales rep picks chats and a start date (`since`), with a real-time progress bar and explicit **pause** and **resume** buttons.
2. **Rate Limit Compliance ([Feature C-5](file:///Users/van.tran/Documents/dev/chat-bridge/docs/spec.md#L156)):** Importing 500 messages must strictly stay under provider limits (Margince: 60 req/min, Sheets: 60 req/min) without unhandled HTTP 429 ("slow down") errors.
3. **Resource & Freshness Budgets ([Section 11](file:///Users/van.tran/Documents/dev/chat-bridge/docs/spec.md#L305-L308)):**
   - 500-message import: time from source to every active sink 95th percentile under 5s per message; peak memory under 400 MB RSS.
   - Real-time SLA: *"A new message shows in the feed within 5 seconds."*
4. **The Head-of-Line Queue Starvation Trap:**
   - Margince accepts a maximum of 60 requests/minute. If a sales rep initiates an import of 2,000 historical messages across several picked chats, delivering these batches takes 30 to 45 minutes under the Token Bucket rate limiter ([ADR 0005](file:///Users/van.tran/Documents/dev/chat-bridge/docs/decisions/0005-outbox-multi-queue-worker-pacing.md)).
   - If real-time incoming messages and historical backfill messages share a single FIFO queue, a new customer message arriving on WhatsApp or Zalo would be stuck behind thousands of historical records, causing a 30+ minute delay and catastrophically failing the 5-second real-time SLA.
5. **Account Safety Risk ([Section 11](file:///Users/van.tran/Documents/dev/chat-bridge/docs/spec.md#L299)):** Unofficial chat libraries (`baileys`, `zca-js`) risk temporary IP bans or account restrictions if historical chat history is queried aggressively in a tight loop.

We evaluated three architectural approaches:
1. **Option 1 (Single Shared FIFO Outbox Queue):** Backfill messages are inserted into `sink_deliveries` with standard FIFO queue ordering.
2. **Option 2 (Dual-Band Priority Scheduling + Checkpointed Cursor Engine):** Dual priority bands (`priority: 10` Live vs `priority: 50` Backfill) combined with a chunked, paused/resumable history cursor engine.
3. **Option 3 (Bypass Outbox via Direct Streaming):** Historical messages bypass the SQLite outbox entirely and stream directly to sink endpoints over HTTP.

---

## 2. Decision

We choose **Option 2: Dual-Band Priority Scheduling with Checkpointed Cursor Engine & Adaptive Connector Pacing**:

```
 [ Live Incoming Chat ]                     [ Historical Backfill Job ]
           |                                             |
           v                                             v
 priority = 10 (High / Live)                   priority = 50 (Normal / Backfill)
           |                                             |
           +--------------------+------------------------+
                                |
                                v
               [ Outbox Table: `sink_deliveries` ]
                 INDEX (sink_id, status, priority, next_retry_at)
                                |
                                v
               [ SinkWorker: Dequeue Batch ]
                 Always drains `priority = 10` before `priority = 50`
                                |
                                v
               [ Rate-Paced Delivery to Sinks ]
```

### 1. Dual-Band Priority Queueing in the Outbox

1. The `sink_deliveries` schema is structured with an indexed `priority` column:
   - `priority = 10` (**Live Real-Time**): Assigned to all live incoming messages passing the filter pipeline.
   - `priority = 50` (**Historical Backfill**): Assigned to messages generated by the history import engine.
2. The covered SQLite index is updated to:
   ```sql
   CREATE INDEX idx_sink_deliveries_polling 
   ON sink_deliveries (sink_id, status, priority ASC, next_retry_at ASC);
   ```
3. When a `SinkWorker` queries for the next batch up to `batchSize`:
   ```sql
   SELECT d.id, d.message_id, d.attempts, m.encrypted_payload, m.iv, m.tag
   FROM sink_deliveries d
   JOIN messages m ON d.message_id = m.id
   WHERE d.sink_id = ? 
     AND d.status = 'pending' 
     AND d.next_retry_at <= ?
   ORDER BY d.priority ASC, d.created_at ASC
   LIMIT ?;
   ```
4. **Zero Starvation Guarantee:** If a live customer message arrives while 2,000 backfill messages are queued, the live message enters at `priority = 10` and is dispatched in the very next delivery tick (< 2 seconds), preserving the 5-second SLA.

### 2. Connector History Ingestion Pacing

To protect personal Zalo and WhatsApp accounts from spam detection:
1. History import queries connectors via `source.history(thread, since)` in discrete pages of **50 messages**.
2. A mandatory **2-second cooldown delay** is enforced between consecutive pagination calls to the chat provider socket.
3. Media payloads are immediately replaced with text placeholders (e.g., `[image: document.pdf, 450 KB]`), discarding binary blobs to keep peak RSS strictly under 400 MB.

### 3. Checkpointed Resumable State Machine

History import progress is persisted in the operational SQLite database in `history_imports`:

| Column | Type | Purpose |
| :--- | :--- | :--- |
| `id` | TEXT PRIMARY KEY | Import task UUID |
| `network` | TEXT | `whatsapp` or `zalo` |
| `thread_id` | TEXT | Chat thread identifier |
| `since_time` | TEXT | ISO 8601 start date selected by the rep |
| `cursor_time` | TEXT | ISO 8601 timestamp of the oldest imported message |
| `status` | TEXT | `running`, `paused`, `completed`, or `failed` |
| `imported_count` | INTEGER | Number of messages successfully ingested |
| `total_estimated` | INTEGER | Estimated total messages for UI progress calculation |
| `last_error` | TEXT | Plain-language failure message if aborted |

- **Pause Action:** Toggling pause in the UI or CLI sets `status = 'paused'`, halting connector pagination after the current 50-message page.
- **Resume Action:** Resuming fetches the saved `cursor_time` and restarts pagination from that timestamp without re-reading or re-delivering already imported messages.
- **Crash Recovery:** If the computer sleeps, loses power, or restarts, any `running` import safely transitions to `paused` upon engine restart and can be resumed with a single click.

## 3. Rationale and Comparison

| Dimension | Option 1: Single Shared FIFO Queue | Option 2: Dual-Band Priority Queueing (Selected) | Option 3: Direct Streaming Bypass |
| :--- | :--- | :--- | :--- |
| **Real-Time Delivery Freshness (< 5s)** | **Violated.** Live messages wait behind thousands of historical backfill messages (30–60 min latency). | **Guaranteed (<2s).** Live messages preempt backfill messages instantly via priority index. | Moderate, but uncoordinated with outbox pacing. |
| **Account Safety (Ban Protection)** | Poor if unthrottled. | **Strict.** Chunked 50-msg pages with 2s cooldown protect WhatsApp and Zalo accounts. | High risk of flooding sockets. |
| **Crash & Resume Safety** | Partial (messages in DB, but pagination cursor lost). | **Crash-Proof.** State held in `history_imports`; seamless resume from exact timestamp cursor. | **Violated.** Memory-only streams lose progress on crash or network blip. |
| **Memory Budget (< 400 MB Peak RSS)** | Can spike if thousands of messages are loaded into memory. | **Bounded.** Paged streaming of 50-message chunks ensures peak RSS stays under 180 MB. | Low, but unbuffered and fragile. |

---

## 4. Consequences and Mitigations

* **Index Size Overhead:** Adding `priority` to the compound SQLite index increases index tree size slightly.
  * *Assessment:* For a 10,000-message outbox backlog, the additional index column consumes under 300 KB of disk space, while providing sub-millisecond query execution.
* **Margince Rate Limit Saturation:** Under continuous historical import, Margince's Token Bucket (60 req/min) will be running at capacity.
  * *Mitigation:* Because priority-10 live messages take precedence, live messages consume tokens first. If a live message arrives when tokens are depleted, it only waits until the next single token refills (at most 1.0 second), well within the 5-second freshness budget.
